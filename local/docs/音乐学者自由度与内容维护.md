# 音乐学者自由度与内容维护规范（2026-11-25 起）

> 适用：第三轮之后的新轮次。第三轮及以前已按旧流程完成，不追溯改派。
> 上位原则仍是[知识库写作偏好](偏好-知识库写作.md)：先读、后想、再写；选题与论点从阅读中生长，不预设题目、结论、篇数或模板。

## 1. 学者不只写新文章，也维护整个 content

后续轮次里，音乐学者的工作对象是**整个知识库**，不只是“本轮新选题清单”。选题来源同时包括：

- `local/resources/` 的教材、论文、原谱、编码与标注；
- `content/` 已有文章、各级 `index.md`、`provenance/` 与 `local/docs/研究归档/`。

学者应在动笔前先翻 content：哪些问题已写过、哪些说法互相矛盾、哪些文章单薄或过时、哪些主题缺入口、哪些段落该合并或拆开。**“重写、补写、拆并、改位置”与“写一篇新文章”具有同等地位**，不是只有净增篇数才算产出。

## 2. 学者可以自由修改 content 中已有内容

- 可以修改任何已有文章，包括其他学者写的文章；不要求只改自己名下篇目。
- 可以改论点、结构、标题、例子、谱例占位、互链与措辞；可以整篇重写，也可以只修一段。
- 修改他人文章前，先在 Team 任务板建维护卡（建议 `M<n>`），写明目标文件、要解决的问题、拟改范围、是否影响 provenance/归档/互链；若该文件已有他人在改，先沟通或换一篇。
- 修改后必须同步更新 `provenance/<同路径>.md` 与 `local/docs/研究归档/<slug>.md`；若中心论点改变，在归档里写清“旧论点 → 新论点/为什么改”，不必保留每一句旧文，Git 历史保留旧版本。
- 修改同样要过门禁：`check_article_acceptance.mjs`、`validate-content.mjs`、`check_notation_fences.mjs`（涉及谱例时），并遵守标题、副标题、占位、许可与“正文不写生产信息”的既有纪律。

## 3. 移动、拆分、合并、重命名、删除：学者提案，主 agent 执行

以下属于**结构操作**，学者不直接动文件系统或 Git，须交由主 agent 执行：

- 移动文章到另一目录/另一轴；
- 把一篇拆成两篇或多篇；
- 合并多篇为一篇；
- 重命名文件或改 slug；
- 删除文章或整段并入他文；
- 新建/删除目录，改站点配置、侧边栏、重定向；
- 批量改 index 收录或跨文件链接。

学者提交 `M<n>` 提案卡，至少写明：

1. 目标文件与目标位置（旧路径 → 新路径）；
2. 为什么要动：内容重复、主题错位、一篇承担了多个问题、文章过长/过短、索引与互链需要；
3. 拆分/合并后的各篇中心问题与边界（不能只是把文件切开）；
4. provenance、研究归档、谱例 id、index、互链的迁移方案；
5. 对已编译谱例与 `score-board` 的影响。

主 agent 审核后执行 `git mv`、拆分建文件、改 index/配置、串行提交；学者在新文件上继续写作。**提案被接受前，学者不要自行移动或删除。** 主 agent 若认为提案会破坏结构，可要求改为“原地重写”或先补论证。

## 4. 自由写作的边界

- 不预设题目、标题、结论、节数、字数、比较作品数量或“每篇必须几个谱例”。
- 可以在研究过程中改变问题、缩小或扩大论点；可以写理论阐释、作品研究、风格比较、史料辨析、编辑重构，也可以写“对某篇现有文章的修正”。
- 不要求每篇都是“新作品分析”；对同一作品写第二篇不同问题的文章是允许的，但要说清与已有文章的分工并互链。
- 不为了轮次篇数凑题；一轮的目标是“把哪些问题推进到什么程度”，不是固定 20 篇。
- 不因“怕改别人文章”而放过明显错误；学术判断优先于作者边界，改动留痕即可。
- 不把主 agent 当选题审批人：主 agent 只协调结构、并发、提交与工程门禁，不替学者决定写什么、怎么写。

## 5. 记录与协作

- 每个维护/写作任务都要有 Team 任务卡，写清范围与验收标准；完成后关闭。
- 同一文件同一时间只允许一个写者；跨文件大改先报主 agent，避免提交时互相覆盖。
- 结构操作由主 agent 串行执行，学者不并发 `git add/commit`。
- 批后复读仍要读整批（含被改写的旧文），重点看理解、论证、跨篇一致性与可读性，不做逐句审计。

## 6. 模型与轮次

- 后续新开的音乐学者使用 `magpie / group/gemini-4-hydrogen`（待该路由在会话中可用后）；当前第三轮遗留任务仍用 `gemini-3.8-flash` 收尾。
- 新轮次不默认“20 篇”；由主 agent 与用户确认本轮是“新写为主”“维护/重构为主”还是混合，再定目标。
- 质量优先于数量：宁可一轮只完成少数几篇扎实的新写与重构，也不凑数。
