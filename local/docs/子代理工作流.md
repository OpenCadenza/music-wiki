# 子代理工作流：预备整理与自由研究

> 2026-11-07仓库结构更新：本开发分支只有一个主仓库，local为普通目录；旧的local独立提交、外层仓库等说法仅描述历史阶段。当前按[团队接手说明](交接/README.md)执行；本轮仍不启动正式写作。

版本：2026-11-07单仓库交接修订；预备轮已完成，按用户最新要求修订。用户要求见[写作偏好](偏好-知识库写作.md)，执行状态见[纠偏重建计划](纠偏重建计划.md)。

资料预备已完成，本轮仅完善文档与准备，交用户检查。正式轮另行启动，不预先从贝多芬或任何作曲家起步。

主线是：**资料可读可找 → 学者实际阅读 → 自主发现选题 → 按需补充资料 → 理解与著述 → 文章成稿 → 看板归档与逐篇版本提交 → 整批结束 → 编辑复读与修订。**

## 1. 预备轮与正式轮分开

| 阶段／职能 | 模型与强度 | 工作 |
| --- | --- | --- |
| 预备轮：资料初步整理 | gpt-6-luna / medium | 导入已有资料后分拣、OCR、抽取与清理、建立可读副本和资料入口 |
| 正式轮：音乐学者 | gpt-6.1-terra / high | 阅读、自主选题、提出资料需求、分析与写作，自主决定文章目录 |
| 正式轮：资料收集助手 | gpt-6-luna / medium | 找资料、保存原件、亲自初整；负责交付谱例的正确性与符合要求，更新阅读库并返回资料 |
| 主控／协调 | 当前主代理 | 调度、共用文件与目录整合、构建、串行提交和恢复 |
| 批后编辑复读 | gpt-6.1-terra / medium；每批正式轮结束后执行 | 整批检查主要理解、论证与可读性；谱例问题交资料助手修正 |

**资料初步整理只存在于预备轮。** 正式轮资料助手遇到新 PDF、网页或谱源，自己整理，不能再把工作转给一个不存在的初整代理。

编辑复读在整批正式轮结束后集中执行，不作为逐篇成稿、归档或提交的前置条件。不设逐句事实审计员或选题审批员。主控可以参与理解和写作，不设“主控不能写正文”的限制。

## 2. 资料库是持续生长的共同研究空间

原文件放 `local/origin_resources/`；面向发现、阅读和调用的副本放 `local/resources/`。

预备轮取得的阅读资料与正式轮助手新增、整理的资料处于同一个资料库，具有同等使用地位。学者随时可以从新增资料发现新的选题，不存在只有预备轮资料才允许选题的白名单。

新资料也要进入共同目录与来源卡，不能只私下返回给提出请求的学者，其他人却无从发现。原始、可读、仅摘要、转换失败等状态如实记录；状态说明可读性，不按“哪一轮取得”划知识等级。

原始库保存完整取得记录，不表示所有文件都是可信文献。旧 AI 文章、自编模型、日志和生成物不进入默认学术阅读入口。

## 3. 预备轮怎样整理已有资料

初整代理逐类处理真实材料，建立有实际内容的阅读副本，不能只输出路径清单：

- 已有 Markdown、正文文本可直接整理；HTML 去除导航和广告，保留正文、图表与来源定位。
- PDF、图片及其他需要转换的非文本文档使用用户指定的 [EverythingMarkdown 说明](C:/Users/ThinkBook/workspace/文档转换与OCR/EverythingMarkdown/README.md)。原件只读，Markdown 和图片输出到阅读库。
- PDF 保留物理页码与可识别的印刷页码关系。分段转换分别保存，避免缓存或同名输出覆盖不同页段。
- 乐谱的 OCR 保留文字与谱面图像，不把 OCR 文本当成可靠音符编码。需要代码时另找真实编码或处理所需片段。
- ZIP 先列内容，再解出可用教材、标注与谱源；大型数据集不盲目全量转码。
- 理论、研究论文、版本导言、作品背景、乐器资料、原谱、编码和标注分别说明实际性质。
- 目录页、搜索摘要、失败下载、空文档不能算作已经取得全文。

每份资料保留简短来源卡：题名／作者、资料类型、原件路径、阅读副本、实际可读范围、章节／页码入口和缺失情况。初整代理不替音乐学者做权威音乐结论。

所有资料转换结果应标记为“已转换／可读”，不虚报为“学者已阅读”。来源卡和索引属于资料层，不复制到知识正文。

## 4. 音乐学者自由发现选题

学者从可读资料中自由探索，不限制作曲家、体裁或主题。主控提供共同写作原则和资料入口，不预设文章题目、结论、作品列表或必须写出的几个答案。

学者实际阅读后发现有价值的问题，记录在公共看板；根据研究继续阅读、调整问题和形成理解。资料入口是起点，可以跨来源、跨作品、跨知识领域探索。

选题记录是让同行了解当前研究，不是等主控逐题批准。相近选题先沟通，必要时共享资料、合并或换角度，避免重复劳动。

学者需分清资料作者的观点、实际音乐现象和自己的推导。允许有根据的独立分析与新归纳，不要求每句分析都在文献里找到同一句话；不得把自拟说法包装成公认理论。

## 5. 学者自主决定文章位置

目录结构采用用户确定的以下方案，不另增 forms、genres 等顶层轴：

~~~text
content/
├── index.md                      # 定位与材料／结构／音响三个尺度
├── techniques/                   # 问题轴：可跨语境推广
│   ├── index.md
│   ├── material/                 # 动机、乐句、主题、细胞
│   ├── structure/                # 曲式、段落、调性布局、终止、比例
│   ├── harmony/                  # 调性关系、和声语汇、半音体系
│   ├── counterpoint/             # 模仿、卡农、赋格、声部进行
│   ├── rhythm/                   # 节拍、速度、节奏型、弹性速度
│   └── sound/                    # 音区、织体、厚度、力度、配器
├── composers/                    # 语境轴：某人某体裁的具体做法
│   ├── index.md
│   └── <作曲家>/
│       ├── index.md              # 总体特点，写音乐实质
│       └── <体裁>/
│           ├── index.md          # 体裁的问题地图
│           └── <选题>.md
├── ensembles/                    # 语境轴：编制的惯例与限制
│   └── <编制>/
├── styles/                       # 语境轴：非作曲家体系的风格
│   └── <风格>/
└── notation/                     # 工具轴：记谱与实现
    └── <主题>.md
~~~

学者根据文章主要解释的问题，自主选择位置，也可以新建子目录。新子目录确有内容后再建立实质导论，不为了凑树预建空页。

文章保留一个主要位置，其他语境以链接关联。同一段谱例只维护一份；相关文章可以链接过去。各级 index 写音乐内容，不维护手工文件清单。

## 6. 正式轮怎样找资料、整理新资料

学者直接通过 Codex 原生消息向资料助手提出请求，说明研究问题、资料用途、需要的文献或作品定位以及接受的形态。小节位置未知时可以请求定位，不先编造范围。

助手依次完成：

1. 先查原始库、阅读库和已有来源记录，避免重复取得。
2. 按需从相关作者、机构、期刊或谱源渠道寻找资料。
3. 新原件保存到 `origin_resources`，保留取得信息和来源关系。
4. **亲自完成初步整理**：网页清理，PDF／图片等用 EverythingMarkdown OCR，必要时解包、转码或整理目标谱段。
5. 可读结果保存到 `resources`，添加或更新共同资料入口。
6. 原生消息回复学者：拿到了什么、是否全文、实际页段、原件与阅读副本的位置、尚缺什么；交付谱例时说明真实定位与已完成的核对／工程检查。

原件保存后但转换尚未完成时，可以先报进度；不能把“有链接”“找到摘要”当作全文交付。复杂的音乐解释交回学者判断，助手概述不能替代原文。

学者收到资料后亲自阅读，也可浏览其他助手新增的资料形成新选题。新资料不会因为出自正式轮而被降低地位。

**谱例正确性和符合要求由资料收集助手负责。** 助手对实际交付片段按可靠原谱核对作品、乐章、小节、音高、节奏、声部、移调和必要上下文，并处理版本、音名、可编译性、标题／定位、速度和GM等既有要求。编译通过不能替代音乐内容核对；核对聚焦本次所需片段，不扩展为全库逐音审计。

找不到满足要求的谱例，助手就如实向学者报告，区分没找到、定位不明、编码未完成或正确性无法确认，并给出实际已知的作品定位。不能把尚不确定的谱例交给学者自行验收，也不能编造谱例或小节号。

**音乐学者无需检验交付谱例是否正确或符合要求。** 学者继续负责资料阅读、音乐理解与文章论证；没有找到的谱例可以用真实定位的占位符表示，未知位置如实注明待定位。占位不替代尚未完成的研究。

## 7. 公共看板记录学者研究全局

公共看板放在 `local/docs/公共看板/`，主要用途是让音乐学者了解彼此做什么。**资料请求和交付使用原生消息，不把看板当任务抢单队列。**

建议结构：

~~~text
公共看板/
├── README.md
├── 在研/                 每个选题一份，由对应学者维护
└── 归档/                 每完成一篇，归档它的研究记录
~~~

在研记录至少说明：学者、选题及当前关注的问题、已读／拟读的资料范围、拟用作品或案例、文章拟放位置、当前进度、缺口，以及其他学者值得知道的重叠或关联。格式从简，不写成固定文章模板。

学者在开始研究、方向明显变化或文章完成时更新自己的记录；开始新选题前先了解其他在研与归档内容。每位学者只改自己的记录，共用说明和全局登记由主控整合。

资料请求的详细往返可存在研究笔记或交付记录里，不在看板重复维护一套认领状态。

## 8. 每篇完成后归档并在主仓库提交

一篇文章成稿，收到助手交付的谱例或如实记录缺谱占位，助手完成谱例相关处理、主控完成必要整合后，音乐学者完成以下收尾。此时不等待批后编辑复读：

1. 更新研究记录，说明最终选题、实际采用的资料范围、正文位置、助手交付的共享谱例／占位及缺口，标记“已成稿，待本批复读”。
2. 把这一条在研记录移入看板归档。其他未完成选题继续留在“在研”。
3. 通知主控申请版本提交，由主控在当前克隆的仓库根目录串行提交 `content/` 与 `local/` 的**全部非忽略改动**，形成该篇完成时的文档快照。
4. 提交说明标明完成文章及归档记录位置。通过 Git 历史查提交号，不为在同一提交中回填自己的哈希制造额外提交。

这按用户确认的范围执行：原始资料、加工资料、旧内容大归档和大型产物继续由忽略规则排除；正文与文档、研究笔记、工具和看板的非忽略改动一起进入主仓库本开发分支历史；阅读入口和catalog轻量索引也纳入Git。共享快照可以包含其他学者当时已落盘的进行中记录，不为“整理提交”覆盖或丢弃它们。

多个学者不得并发操作同一个 Git index。学者发起收尾请求，主控依次完成 add／commit；提交失败保留归档和工作树，修复后继续，不能冒称已形成版本。

`content/` 与 `local/` 同属一个主仓库；local没有独立.git。逐篇提交同时保存正文与研究过程，不自动推送或发布。本开发分支不整体合入main，发布另行选择审核后的正文改动。

## 9. 阅读、写作与编辑怎样衔接

每个选题可有一份自由格式研究笔记，保存实际读过的页段、关键发现、资料观点与自己的理解、中心论证及缺口。记录从简，不逐句建立出处表，不设最低来源数量。

学者形成理解后，自主决定文章结构和篇幅。理论阐释、背景、风格、作品研究和创作操作都可以写；形式服务于内容。

缺谱例代码时可保留作品／作品号／乐章／真实定位的占位。关键材料没读到、中心解释尚不成立时，继续研究、缩小论点或保存研究稿，不能用模型记忆补出完整正文。

**每批正式轮结束后，由 gpt-6.1-terra / medium 承担编辑复读。** 第一批约20篇文章成稿并逐篇归档、提交后，再集中阅读这一批。复读聚焦主要理解、推理、跨篇关系与可读性，仅对影响论点的疑点回看资料或谱面，不逐句逐音审计，也不抹掉作者有根据的原创理解。

论证或表达问题交音乐学者修订；谱例正确性与要求不符的问题交资料收集助手修正，不让学者重复验谱。编辑复读不替代助手的谱例责任。

批后修订完成后更新已归档记录中的复读状态，记录结果，再由主控在主仓库串行提交content与local全部非忽略改动；保留原有逐篇版本，不改写历史。

主控在content内整合共享谱例与目录导论，执行既有必要工程检查。来源与许可先保存到local；当前正式轮不修改根NOTICE。编译通过只说明工程可用性，不能替代实际阅读或证明全部音乐内容正确。

## 10. 原生通信、并发与恢复

当前运行时提供 spawn_agent、send_message、followup_task、wait_agent、list_agents、interrupt_agent。优先使用这些原生能力；看板只是持久研究状态，不承担自动通知和唤醒。

正在运行或等待消息的代理通过 send_message 继续交流；已结束回合的非根代理通过 followup_task 恢复。具体语义以当次运行时为准。消息给出问题、资料路径和缺口，不贴整本资料。

按指定模型启动，跨模型子代理使用当前工具要求的 `fork_turns="none"`，启动消息明确给出必要上下文、入口和通信对象。

当前并发上限为含主代理的 4 个活跃代理：

- 预备轮：主控加若干初整代理，可分担文字、OCR、谱源等工作。
- 正式轮写作期间：主控加音乐学者和资料助手；没有初整代理，不并行安排逐篇编辑复读。
- 整批结束后：安排gpt-6.1-terra / medium集中复读，学者与资料助手按各自责任处理修订。

中断后先查看看板、处理记录和实际代理状态。原代理可恢复就续做，否则创建新代理并给出准确续接位置。不重复派活，不把处理完成、实际阅读、写作完成、已提交与已发布混为一件事。

## 11. 正式轮的启动边界

迁入后的原始库、经过整理的阅读库、资料入口与明确缺口已交付；本轮完善工作流，用户检查后再另行启动正式轮。

正式轮第一批目标为约20篇文章，选题完全自由，不预设作曲家、体裁、篇目或结论。逐篇完成研究、谱例交接／缺谱占位、看板归档和版本提交，整批结束后再按上述配置集中复读。约20篇是批次规模，不用凑篇数替代理解和质量。后续按有价值的问题持续生长。

新文章的实际创作检索收益，在正式轮有内容后再验证。当前没有启动学者写文章或生成仿作。

## 12. 正式轮改动范围与本轮边界

单仓库正式轮允许维护 `content/` 与 `local/` 研究区，适用于学者、资料助手、编辑和主控；其余站点工程文件不在写作改动范围。不修改根README、NOTICE、脚本、站点配置、CI或其他content外文件。

local是主仓库中的普通本地工作目录，不能另建独立Git仓库。原件、加工资料、研究笔记、公共看板与文档照常维护；原件与阅读正文等重资料仍忽略，入口与catalog索引纳入Git。临时转换和辅助工具放在local，不为解决工程问题越界修改外层工具链。

来源、许可与取得记录先保存在local，不为了绕过范围限制塞进音乐正文。根NOTICE等公共登记的同步留作后续单独安排；现有检查若受旧贝多芬页面等假设影响，就记录具体问题，不补造文章或改脚本来通过检查。

本轮仅完善local/docs中的规则与准备，不改content，不启动正式学者、资料收集或编辑复读，不写首批文章，不推送或发布。
