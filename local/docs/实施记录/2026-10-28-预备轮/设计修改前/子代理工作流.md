# 新子代理工作流：从阅读到文章

设计日期：2026-10-28。用户要求见[写作偏好](偏好-知识库写作.md)，实施顺序见[纠偏重建计划](纠偏重建计划.md)。本页取代旧工作流，当前仍是待实施的设计。

主线是：**可读的资料 → 学者实际阅读 → 发现选题 → 围绕选题补充研究 → 形成理解 → 写成文章 → 编辑复读 → 整合发布。**

乐谱的收集和转换服务于研究。不能再由“已有哪几份 LilyPond 源码”决定知识库能讲什么。

## 1. 团队怎样组成

| 职能 | 模型与强度 | 主要责任 | 交付 |
| --- | --- | --- | --- |
| 资料初步整理 | gpt-6-luna / medium，用户指定 | 分清资料类型，按需解包、抽文本、建立可找的入口 | 可读副本、来源卡、失败与待处理记录 |
| 音乐学者 | gpt-6.1-terra / high，用户指定 | 实际阅读、自由选题、提出资料需求、分析、写作 | 文章、简短阅读与论证笔记、用到的资料和谱例登记信息 |
| 资料收集助手 | gpt-6-luna / medium，用户指定 | 搜索、下载、查找具体页段或谱源，处理转换 | 原文件、可用副本、路径和定位、未解决的缺口 |
| 主控／协调 | 当前主代理 | 维护整体方向、调度、去重、共用文件、恢复与整合 | 真实进度、共享登记、可发布内容 |
| 编辑复读 | 建议按需由另一名 gpt-6.1-terra / high 承担，也可由主控承担 | 检查是否读懂资料、论证是否成立、文章是否好读 | 有实质意义的修改意见，必要时回到关键资料复读 |

前三项是用户指定的角色。**建议增加的是独立的编辑复读职能，不必常驻一个新代理。** 它要防止“读了一个标题就写成文章”和“把自拟说法冒充共识”，同时允许作者有根据地分析。

不再额外常设逐音校谱员、逐句事实审计员、选题审批员。构建和谱例处理由助手与主控按需完成。主控可以参与理解和写作，不设“主控绝不能写正文”的禁令；自己写的试稿有条件时交他人复读。

## 2. 先让资料可读，不把所有资料加工完才开工

原文件进入 `local/origin_resources/`，初步处理结果进入 `local/resources/`。

初整代理先处理一小批能用于试写的资料：教材章节、作曲家／作品研究、谱源各有可用入口即可。其余资料持续整理，避免先花很长时间把全库转成统一格式。

处理规则：

- Markdown、文本和有效 HTML 优先直接读取；网页去掉导航和广告，保留题名、正文与原始定位。
- PDF 先判断能否抽到可读文字。保留物理页码与印刷页码的对应；扫描页按需要 OCR，关键图表仍指回原页。
- 乐谱 PDF 的文字抽取不能还原谱面。保留图像／页码入口，另找编码或按所需片段转录。
- ZIP 先列内容，按研究需要解出相应文献或谱集；大型数据包暂不全量转换。
- 标注数据、Kern、MusicXML、ABC、LilyPond 各保留本来意义。理论、分析、原谱、编码、数据集、网站目录页不能混作一种资料。
- 旧 Agent 笔记、自编模型、旧文章、日志、空下载和失败页面不作为可信音乐文献进入学者的默认资料入口。原样保留在原始迁入快照或历史区即可。
- 所有转换都写新副本，不覆盖原文件。转换失败不编造正文，不把目录页或摘要说成全文。

每份可用资料保留一个很短的来源卡：作者／题名、类型、原始位置、阅读副本、可读范围、章节／页码入口、已知缺失。卡片帮助发现资料，**学者仍要打开正文**。初整代理不负责替学者做权威音乐结论。

目录索引、来源卡和加工状态是资料层的工具，可以存在；知识正文不需要复制这些东西。

## 3. 音乐学者怎样自由探索

启动时只交代共同写作原则、资料入口、当前已有选题和自己的工作文件位置。可以给一份资料作为起点，不预先规定文章标题、结论、作品名单或必须讲出的三五个答案。

学者先读一部分资料。遇到值得解释的矛盾、关联、写法、背景或作品特点，形成选题。简短说明“我读到了什么、想讲什么、为什么值得讲”，落入研究笔记和看板，供团队避免重复。

这一步是通报研究方向，不是逐题等主控批准。遇到撞题时相互交流、合并或换角度；研究方向可以随着阅读改变。

接着围绕选题加深阅读，比较必要的作品和研究。由学者判断：

- 资料实际说了什么，其适用范围在哪里；
- 音乐现象怎样运作，哪些观察可以由谱面支持；
- 自己的解释怎样从这些材料推出；
- 读者需要先理解什么，怎样的叙述顺序最清楚。

不要求读完整本书才准写，也不能只看搜索摘要或初整代理的概述便声称理解了该问题。

## 4. 学者怎样请求资料助手

缺资料时，学者描述自己要解决的问题，例如“需要某论文中讨论这一段结构的正文”和“需要这部作品此乐章的谱面及可转码源”。请求说明用途，便于助手识别真正相关的结果。

最小交接信息是：请求人、研究问题、所需资料或作品定位、接受的替代形态、返回位置。小节范围不确定时可以请助手定位，不能为派任务先编一个范围。

助手依次查：

1. 原始库、阅读库和已有资料记录，避免重复下载。
2. 文献自己的引用、机构／作者页面、乐谱仓库等相关渠道。
3. 新资料获取后先保留原始文件和来源信息，再做需要的阅读或谱例副本。

助手回复要说明：拿到了什么、是否全文、在哪里、对应哪些页段／乐章，尚缺什么。找到搜索结果、目录、摘要或一个失效链接，均不能作为“全文已取得”交差。

助手可以完成必要的解包、格式转换和短谱例处理；复杂分析交回学者。先交付已能阅读的资料，不必等全部格式都变成 LilyPond 才回复。

学者收到资料后亲自阅读并决定是否采纳。助手的摘要是线索，不能代替原文成为文章的知识依据。

## 5. 阅读记录多轻才够用

每个选题一份自由格式笔记，建议放在 `local/workbench/research/<选题>.md`，只留下后续会用的信息：

- 实际读过的资料、页段或乐章范围，以及本次发现。
- 资料作者的重要观点和自己的理解；有争议时保留差异。
- 文章的中心解释，以及支撑它的材料或音乐观察。
- 采用哪些谱例，已有共享片段在哪里，仍需补什么。

不要求逐句建立论断表，也不设最低来源数量。一个集中问题可以从一份扎实资料展开；跨作品、跨时期或概括风格的主张，通常需要更广的阅读。用多少资料由问题决定。

“未读”“选读到哪里”“只看到摘要”要如实写。研究笔记可以很短，但不能批量生成虚假的已读记录。需要引用原话时回看原文，公开文章以自己的表达为主。

## 6. 写作与缺口处理

学者在形成理解后写文章，自定标题、结构、篇幅和叙述方式。正文可先在 `local/workbench/drafts/` 形成，再由主控整合进入 `content/`。

需要代码谱例时，优先复用已登记的真实片段或请助手处理目标片段。长度服务于解释，不做每篇谱例数或小节数配额。

缺口分两种处理：

| 缺什么 | 怎样继续 |
| --- | --- |
| 已读到作品与分析，暂时没有可嵌入代码 | 文章可以完成，相应位置保留真实定位的谱例占位 |
| 关键材料尚未读到，中心判断还站不住 | 补充研究、缩小论点或保留研究稿；不能凭模型记忆补出“完整正文” |

一般背景说明也应来自实际阅读。允许独立分析，不要求找到文献中完全相同的结论；作者要能解释推理，不能用“这是我的理解”免除论证。

## 7. 编辑复读与工程整合

作者先把文章通读一遍，检查自己是否真的把问题讲清。编辑复读再看三件事：

1. **理解**：主要依据确实读过吗？有没有误读、把摘要当全文、扩大来源结论或循环引用旧 Agent 文章？
2. **论证**：主要解释能由资料与音乐现象支持吗？自己的分类有没有被写成公认理论？
3. **文章**：读者是否能顺着思路理解音乐？有没有堆材料、套格式、空泛评价，或过早转成操作清单？

只对影响论点的疑点回看原文或谱面，不开展每篇逐句逐音审计。编辑意见应改进解释，不能把所有原创理解都退回成资料摘抄。

主控统一处理文章归属、共享谱例链接、目录导论、NOTICE 和构建。学者与助手只写各自拥有的文件，通过消息交付共用文件需要的改动，避免同时编辑目录页和总登记。

工程检查保持已有必要项：2.26.0／english、自包含、标题定位、tempo、各声部 GM、链接、重复谱例与编译。检查通过只代表可用性，不替代阅读和理解。没有代码的合理谱例占位可以保留。

## 8. 通信：原生消息交接，公共看板保留状态

**当前会话的运行时已经提供原生团队工具。** 学者、助手和主控可以在同一代理树内互相传递消息，共享本地文件；这不等于任意两个独立侧栏聊天都自动互通。

当前实际工具的用法：

| 工具 | 用途 |
| --- | --- |
| `spawn_agent` | 创建子代理 |
| `send_message` | 给已有代理发消息，不启动闲置代理的新回合 |
| `followup_task` | 给已有的非根代理追加任务，必要时启动或恢复它 |
| `wait_agent` | 等待本代理的消息更新 |
| `list_agents` | 检查代理状态 |
| `interrupt_agent` | 中断代理的当前回合 |

工具语义以当次运行时为准。相关背景见 [OpenAI 多代理文档](https://developers.openai.com/api/docs/guides/responses-multi-agent)；Codex 的模型与角色配置见[官方子代理文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)。本设计没有把 API 默认并发数当成本机限制，也没有依赖另建多代理服务。

推荐交接方式：

1. 学者落盘一个资料请求，再发原生消息通知主控；主控将它分配给可用助手。已有专属助手时可直接交接。
2. 助手先保存资料与返回说明，再通知学者与主控。消息里给路径、定位和剩余缺口，不贴整本资料。
3. 学者正在等待消息时继续原回合；学者已结束回合时，由主控用追加任务恢复它，并附上资料路径。

模型启动时明确使用用户指定的模型和强度。当前工具要求改变子代理模型时采用 `fork_turns="none"`，因此把必要的文档路径、任务背景和通信对象明确写进启动消息，不能假设它继承了本聊天。配置不可用时报告实际限制，不静默替换模型。

公共看板建议放在 `local/docs/公共看板/`，一个请求一份文档。最少记请求人、用途、状态、负责人、资料返回位置和未完成事项。状态使用“待分配 → 已认领 → 已交付 → 已验收”；确实未取得则写清缺口。

正常情况下由主控独占更新看板状态，学者和助手通过原生消息请求更新，各自写自己的研究／交付文件。这样不需要多个代理争抢同一张表。

看板能跨中断保留状态，**它本身不会产生通知，也不会让代理自动醒来**。本轮不创建定时轮询或后台常驻服务。

如果未来运行时没有原生消息，主控在派活和恢复时读取看板并逐个分配；不用让助手同时改“已认领”。若确需多助手自行抢单，再补原子认领机制，不能把多人读后写同一文件当成可靠锁。

## 9. 并发与恢复

当前运行时最多同时活跃 4 个代理，含主代理。初始可采用：

- 资料准备期：主控＋初整＋学者＋助手。
- 稳定生产期：主控＋两名学者＋共享助手；编辑复读按批次接替一个空闲位置。

这是起步配置，不是永久“写手最多两个”的教条。主控统一分配并发额度，学者发布资料请求，不无限向下再开助手。

助手繁忙时，学者可以继续读其他相关章节、梳理论点或改写已理解部分；若资料决定主旨，就保存进度等待，不能赶着“立刻交稿”。

每次得到重要资料、确定选题或交出草稿时落盘。中断后主控先读看板、研究笔记和交付文件，再检查代理状态；原代理可恢复就继续，已丢失则创建新代理并给出准确续接位置。代理 ID 是运行期地址，不是永久知识记录。

## 10. 先用小批文章证明流程有效

先选几份不同类型的可读资料，让学者自由形成一小批选题。建议试写三篇，分别观察理论阐释、作品／风格研究、真实谱例结合的效果；这只是验证覆盖面的安排，不预先指定答案。

试写要检验：作者实际读到什么，原有看法是否被阅读改变，文章是否比资料摘要更清楚，助手能否及时交回资料，记录能否支撑接手恢复。

再让一个 Agent 用新文章辅助创作，回报检索了哪些文章、获得哪些具体认识、在哪里仍无从下手。创作试验放在工作区，不当作真实原作谱例进入知识库。

通过这一步再扩大到奏鸣曲和贝多芬其他分支，逐渐发展通用理论、技法、体裁、编制及其他作曲家知识。不用篇数、编译数或漂亮的看板替代内容质量。
