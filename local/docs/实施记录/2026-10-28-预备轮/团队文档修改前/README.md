# Music Wiki 知识生产：把一个「创作问题」写成文章

> **给谁读**：想给知识库写文章、配谱例、核对来源的人。不会写代码也能参与。工程构建与发布在[页面部署](../music-wiki-页面部署/README.md)；刚加入团队先读[仓库根 README](../README.md)。
>
> 本页是**全局设计**：库长成什么样、文章该写成什么样、你能做什么。
> 当前进度、缺口与待办在[交接要点](handover.md)。

---

## 1. 这里产出的东西是什么

Music Wiki 是一个作曲知识库，它只回答一个问题：**你手上有一个音乐想法，接下来该在谱面上做什么。**

所以这里的文章不是音乐史，也不是乐评。每一篇只讲清**一个具体的创作动作**——比如「开头两小节怎么立住主题」「展开部怎么处理动机」——并且用**真实作品的真实乐谱**把这句话落到小节上。

这些文章有两个读者：想学作曲的人，和写谱的 AI。AI 会把文章当教材读，所以写错一个地方，会被反复学走。

## 2. 整体架构

### 2.1 这一版之前的设计，以及它哪里不成立

项目早期有过一版多轴设计，顶层八个目录：

```
composers/   ensembles/   forms/   styles/
techniques/  notation/    knowledge/   _maintenance/
```

它对了一半：**作曲知识确实是多维的**——问「这段怎么配器」和问「贝多芬四重奏怎么写」，走的是不同入口。
但它有三个问题：

1. **各轴体量极不均。** `composers/` 70 篇，`ensembles/` 6 篇、`forms/` 4 篇、`techniques/` 5 篇。
   差两个数量级，说明这些「轴」不是同一层级的东西，被强行平铺了。
2. **平铺必然重复。**「四重奏织体」同时属于 `ensembles/string-quartet`、`techniques/`、
   `composers/beethoven/quartets`。三处都写是三份会分叉的稿子；只写一处，另外两处就空着。
3. **`knowledge/` 与 `_maintenance/` 是元信息**（stable-ids、迁移记录），不该出现在正文目录里。

### 2.2 关键洞察：轴分三类，不是一类

| 类别 | 回答 | 轴 |
| --- | --- | --- |
| **语境轴** | 为**谁**、为**什么编制**、在**什么风格体系**里写 | `composers/`、`ensembles/`、`styles/` |
| **问题轴** | 你**卡在哪个问题**上 | `techniques/`（六个维度） |
| **工具轴** | 怎么**落到谱面上**（记谱、移调、MIDI） | `notation/` |

语境轴与问题轴的区别不是分类学上的，是**结论的适用范围**：

- 问题轴的结论**能推广到别的作曲家**（「推迟终止有四种手段」对莫扎特也成立）；
- 语境轴的结论**只对这个人/这个编制成立**（「贝多芬在 Op.111 里把中音区留空」）。

### 2.3 核心规则：一篇文章只有一个物理位置

这是整套架构唯一必须守住的规则。**一篇文章只能写在一条轴上，其余轴用链接指过去。**

归属判据（按顺序问）：

1. 这篇文章的结论**换个作曲家还成立吗**？成立 → 问题轴；不成立 → 语境轴。
2. 它的**主要证据**是某个人的作品，还是多人、多编制的对照？前者 → 语境轴，后者 → 问题轴。
3. 两边都像 → **拆成两篇**：问题轴写判据（用两个短例），语境轴写个案（用一个完整段落），
   互相链接，**例证不重复**。

「通则」与「个案」不是同一篇文章的复制，是两种不同的东西。这条规则保证两轴都有人写，且不会分叉。

### 2.4 目录结构

```
content/
├── index.md                      # 库的定位与三个尺度（材料 / 结构 / 音响）
│
├── techniques/                   # 问题轴：结论可跨语境推广
│   ├── index.md
│   ├── material/                 # 动机、乐句、主题、细胞
│   ├── structure/                # 曲式、段落、调性布局、终止、比例
│   ├── harmony/                  # 调性关系、和声语汇、半音体系
│   ├── counterpoint/             # 模仿、卡农、赋格、声部进行
│   ├── rhythm/                   # 节拍、速度、节奏型、弹性速度
│   └── sound/                    # 音区、织体、厚度、力度、配器
│
├── composers/                    # 语境轴：某人某体裁的具体做法
│   ├── index.md
│   └── <作曲家>/
│       ├── index.md              # 这个作曲家的总体特点（音乐实质）
│       └── <体裁>/
│           ├── index.md          # 这个体裁的问题地图
│           └── <选题>.md
│
├── ensembles/                    # 语境轴：编制本身的惯例与限制
│   └── <编制>/                   # orchestra / string-quartet / choir / piano
│
├── styles/                       # 语境轴：非作曲家体系的风格
│   └── <风格>/                   # jazz / modern / popular
│
└── notation/                     # 工具轴：记谱与实现
    └── <主题>.md                 # 移调乐器、MIDI 音色、LilyPond 惯例
```

**六个技法维度怎么分工**——这是问题轴内部唯一需要记住的东西：

| 维度 | 装什么 | 典型判据 |
| --- | --- | --- |
| `material/` | 动机、乐句、主题 | 一个动机改几个参数还算它 |
| `structure/` | 曲式、段落、比例、终止 | 段落地图怎么排、终止什么时候该来 |
| `harmony/` | 调性关系、和声语汇 | 半音往哪走、调怎么转 |
| `counterpoint/` | 模仿、卡农、赋格 | 几条线怎么各自成立 |
| `rhythm/` | 节拍、速度、节奏型 | 脉动由谁维持 |
| `sound/` | 音区、织体、厚度、配器 | 谁在加倍谁、中间空不空 |

> 体裁（sonata、四重奏）与曲式（sonata form、rondo）不同：体裁是「写什么」，曲式是「怎么分段」。
> 体裁的写作惯例写在各作曲家分支的 `index.md` 与 `structure/` 里，不单独设轴。

### 2.5 空轴不建目录

架构是完整的，但**没有内容的轴不要创建目录**。构建会检查「每个目录都要有 index.md」，
空目录会变成负担。所以 `ensembles/`、`styles/`、`notation/` 三个轴现在都还没建——
等有第一篇真正属于它们的文章，再建目录。

### 2.6 作曲家轴：以贝多芬为例

```
content/composers/
├── index.md
└── beethoven/
    ├── index.md                     # 贝多芬关心什么问题、用什么手段
    ├── piano/
    │   ├── index.md
    │   └── sonatas/                 # 17 篇
    ├── quartets/                    # 6 篇
    ├── chamber/                     # 6 篇
    ├── concertos/                   # 2 篇
    ├── symphonies/                  # 2 篇
    └── overtures/                   # 1 篇
```

**什么时候加中间层**：只有当一个作曲家的某类作品多到需要二级体裁时才加。贝多芬是
`piano/sonatas/`——钢琴作品量大，下面还要分奏鸣曲、变奏曲、小品。
其他作曲家一般直接 `composers/<作曲家>/<体裁>/`。

**体裁名用读者会说的那个词。** 贝多芬的分支是 `piano`、`quartets`、`chamber`、`concertos`、
`symphonies`、`overtures`——前两个是编制、后四个是体裁，因为它们各自是乐迷与作曲者的常用入口。
这里不追求分类学一致。

### 2.7 选题与作品是多对多

- **一个选题可以取多部作品的片段。**「配器分层」同时用 Op.92 的引子与 Op.67 的第一乐章。
- **同一部作品的不同片段可以出现在不同选题里。** Op.2 No.1 第一乐章出现在五篇文章中，
  分别讲开头、动机、连接部、副部、结束部——**每篇取不同的小节**。
- **但同一段谱例全库只出现一次。** 多对多不等于重复；范围重叠时让给讲得最细的那一篇，别处用链接。

这条约束是技术性的：谱例按代码哈希查 manifest，重复会串号。

### 2.8 每级 `index.md` 写什么

| 层级 | 写什么 | 不写什么 |
| --- | --- | --- |
| 根 | 库的定位、三个尺度、怎么用 | 文件清单 |
| 作曲家 | 这个作曲家的总体特点：他关心什么问题、用什么手段 | 检索方法、证据边界、目录列表 |
| 体裁 | 这个体裁的结构问题地图：哪些位置必须做决定 | 作品列表 |
| 技法维度 | 这个维度的核心判据、与其他维度的边界 | 索引 |
| 编制 / 风格 | 这个编制、风格的限制与惯例 | 作品清单 |

OpenViking 已有路径 / 向量 / 关键词三套检索，站点侧边栏自动生成——
**正文与目录页都不需要帮检索做事**。

### 2.9 命名约定

- **目录**：小写英文、kebab-case。
- **文章 slug**：小写英文、kebab-case，**用选题命名，不用作品号**。
  `opening-gestures`、`motive-tasks`、`double-exposition`、`postponing-the-cadence` 是好名字；
  `beethoven-op2-no1` 不是——那是作品，不是选题。
- 例外：`op90-two-movements` 这类，作品号进入 slug 是因为选题本身就是「两乐章方案」，
  作品号只是限定语。

### 2.10 扩展位

| 扩展 | 怎么加 |
| --- | --- |
| 其他作曲家 | `composers/<作曲家>/<体裁>/`，规则完全一样。起步五步见[交接要点](handover.md) |
| 贝多芬其他体裁 | `piano/variations/`、`songs/`、`choral/`、`opera/` |
| 编制轴 | 有了第一篇编制类文章（如「管弦乐队怎么写」）再建 `ensembles/orchestra/` |
| 风格轴 | 有了爵士/流行第一篇文章再建 `styles/` |
| 工具轴 | 移调乐器、MIDI 音色这类主题攒够两篇再建 `notation/` |
| 技法六维 | 现有三篇平铺，按 §2.4 的表拆进 `material/`、`structure/` |
| 跨作曲家技法 | **最该做的一步**：现在技法层只有贝多芬例证，换成莫扎特、勃拉姆斯、德彪西才是它真正的价值 |

## 3. 一篇合格的文章长什么样

三件事缺一不可：

1. **一个动作，不是一个话题。**「贝多芬晚期风格」是话题；「晚期奏鸣曲开头怎么用碎片动机起句」是动作。
2. **能用 2–3 部作品证明。** 至少两段真实谱例，最好来自不同作品、不同时期。
3. **读者读完能动手。** 有可复制的做法，而不只是「这里很妙」。

配上 8–20 小节的真实谱例，标清来源，就可以动笔了。细节见[选题与写作方法](writing-rules.md)。

**自检判据**：一句话如果给不出「第 N 小节 + 音名 + 拍位」，它多半是评论而不是知识。

## 4. 你能做什么

| 你的角色 | 具体能做的事 | 第一步 |
| --- | --- | --- |
| 读者（零门槛） | 读文章、挑错、检查谱例能否播放、链接是否断 | 打开[线上知识库](https://opencadenza.github.io/music-wiki/)，边读边记 |
| 会写作 | 按选题写一篇新文章，或把已有文章讲不透的地方补深 | 读[选题与写作方法](writing-rules.md)，从「一篇文章的骨架」开始 |
| 会一点 LilyPond | 把缺谱例的占位补上真实乐谱 | 看[交接要点](handover.md)的缺口表，按[配货管线](score-pipeline.md)操作 |
| 细心、懂版权 | 核对谱例来源与许可，维护 `NOTICE.md`（没有仓库写权限就把条目交给维护者） | 读[资料来源](sources.md)的「许可登记规则」，对照 `NOTICE.md` 查漏 |

## 5. 第一次上手：补一处占位

这是目前最缺人、也最容易看到成果的活。**第 3 步起要跑命令行**；不方便装环境就做到第 2 步，把原始乐谱和来源信息交给维护者。

1. **挑一处。** 打开[交接要点](handover.md)的缺口表，挑说明写着「换有源作品替代」的一条
   （例如把 Op.109 III 换成有源的 Op.49 No.1 II）。
2. **找源。** 按[资料来源](sources.md)去 Mutopia（主力）或 IMSLP（兜底）下载真实乐谱；**不要用 MuseScore 用户上传谱**。
3. **配货。** 按[配货管线](score-pipeline.md)把原始乐谱变成能编译、能切片的源码：迁到 LilyPond 2.26.0、编译零 error、音名转 english。
4. **切片、嵌入、登记、提 PR。** 切出 8–20 小节填进占位，代码块补齐 `title`/`location`、`\tempo`、`midiInstrument`；来源写进 `NOTICE.md`，然后按[发布流程](../music-wiki-页面部署/publishing.md)提 PR。没有写权限就先 Fork；完全不会用 GitHub，就把源文件和 `NOTICE.md` 条目交给维护者代为提交。

整条链路长这样：

```mermaid
flowchart LR
  A["找到一份公开乐谱"] --> B["变成能编译的版本"]
  B --> C["切成 8–20 小节"]
  C --> D["写进文章、登记来源"]
  D --> E["提 PR、CI 编译"]
  E --> F["上线，并可被 AI 检索"]
```

> 拿不到谱例不算失败：正文照写，谱例位置留「占位行」，把来源链接登记进 `NOTICE.md`。**占位比缺页好。**

## 7. 五条别踩的坑

- **不要凭空写谱例。** 没有真实来源就写占位，不要自己编一段「贝多芬风格」。
- **不要因为拿不到乐谱就删掉选题。** 占位比缺页好，补谱不用重写正文。
- **不要在校验音高上耗时间。** 构建只保证编译通过，音乐内容由人工复核。
- **不要把来源、版次、免责声明写进正文。** 它们统一进 `NOTICE.md`。
- **不要复制同一段谱例到两篇文章。** 用链接指向已有文章。

构建能通过，不等于内容正确，也不等于版权合规——后两件事只能人来看。
