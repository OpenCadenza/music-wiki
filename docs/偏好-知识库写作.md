# 知识库写作偏好（通用，不限贝多芬）

> 从本项目的多轮沟通里提炼。做知识库/文档类任务时先读这一页。
> 具体到贝多芬的交接见 `贝多芬-知识库-交接.md`。

---

## 一、最核心的一条

> 身份应当类似**音乐学者搜集资料，缮写音乐专著**，而非机械的资料收集工人。

这条适用于所有知识库：**产出要像人写的专著，不像资料搬运的产物。**
判断标准是"读完能不能动手"，不是"格式是否整齐"。

---

## 二、要内容，不要形式

- **不要固定模板。** 只约束必须约束的东西（能编译、能检索、不重复），其余结构让写作者按内容决定。
- **形式约束过多会导致内容形式化。** 一旦模板规定了"每篇必须有五个小节、每节三段"，
  写手就会去填格子，而不是去想音乐。
- **不要元信息。** 检索词、来源、证据边界、免责声明、ID 表、别名表——这些不进正文。
  它们属于构建记录与协作文档。OpenViking 已经有路径/向量/关键词三套检索，正文不需要帮忙。
- **index.md 写实质内容**，不写文件清单与检索指引。

## 三、不许编

- **案例必须真实。** 没有真实案例就写占位（保留作品、作品号、乐章、小节范围），
  **不要自己编一个"某某风格"的示例**。
- **不要因为找不到案例就放弃选题。** 占位比缺页好，补案例不用重写正文。
- **许可不是障碍。** 能用就用，把来源与许可记到专门的登记文件里。

## 四、不要过度防御性编程

这是本项目前身失败的原因，用户原话是"学术上无懈可击，对写谱的人毫无用处"。

具体表现：
- 整篇在讲来源可信度、证据边界、"这不代表原作"；
- 第一条可执行指令出现在全文 87% 处；
- 因为校验不过就放弃例子。

对策：
- **校验交给人工。** 机器只保证"能编译/能运行"，不保证"内容正确"。
- **进度优先。** 不要在逐字比对上花的时间超过写作本身。
- **出错就改，不要预先设防。** 用户会指出错误，改了就行；写一堆免责声明挡不住错误。

## 五、可执行性判据

一句话如果给不出「具体位置 + 具体对象 + 具体数值」，它多半是评论而不是知识。

音乐：第 N 小节 + 音名 + 拍位。
代码：文件 + 函数 + 行号。
数据：指标 + 数值 + 口径。

给不出，就删掉或者补上。

## 六、协作方式

- **给规则，不给模板。** 派活时写清"必须讲清哪几个点"，不要写"按 XX 风格写"。
- **任务书要具体。** "三种做法各自适合什么段落"能派活；"讲清楚配器"派不出活。
- **小批量并行。** 一次派太多代理，会在交付前被系统中断、空手而归；每批 ≤2 个，
  并要求"拿不到就写占位、立即交稿"。
- **写完自己读一遍。** 如果自己都不想照着改，就是没写成，回去重写。

## 七、文档怎么写

- **说人话。** 先讲结论与理由，再讲步骤；不要一上来就是表格与清单。
- **给正反例。** "不要写空话"是抽象要求；给一句反例一句正例，才有人照做。
- **承认踩过的坑。** 把自己的错误写进文档，比藏起来有用得多。
- **区分受众。** 团队协作文档写全局（别人要知道自己该做什么）；
  个人/单块细节写进 `local/`，不污染团队文档。
