## 3. 新开一个作曲家，怎么起步

以「想加巴赫」为例，五步：

1. **先摸源，别先写。** 去 [Mutopia](https://www.mutopiaproject.org/) 或 IMSLP 看这个作曲家
   有哪些机器可读的 LilyPond / MusicXML 源。**这一步决定后面能写多深**：没有源就只能大量占位。
   摸完把结论写进[资料来源](sources.md)。
2. **配货。** 按[配货管线](score-pipeline.md)把选中的作品变成「2.26.0 + english 音名 + 编译 0 error」
   的源码。这一步不做音高校验，编译通过即可。
3. **定体裁与选题。** 建 `content/composers/<作曲家>/<体裁>/`，写 `index.md`。
   **`index.md` 写这个分支的音乐实质**（这个作曲家在这个体裁里值得追的问题），
   不写文件清单、不写检索方法。
4. **写第一批 3–5 篇。** 每篇 1500–3000 字、1–2 个谱例。第一批的作用是**定这个分支的调子**，
   后面所有篇都跟它对齐。
5. **登记来源**，跑通四步构建，提 PR。

前两步做完之前不要派写手——写手在没有源的情况下只能写占位，或者更糟：自己编谱例。

## 4. 全局风险

1. **素材源不稳定。** Mutopia、IMSLP、OpenScore 都匿名可下、无配额，但目录结构、许可标注、
   文件命名随时可能变。**配货前先列目录确认，不要照抄文档里的路径。**
2. **Mutopia 覆盖不全。** 贝多芬 40 个作品目录里没有 Op.35、没有晚期钢琴奏鸣曲、没有声乐。
   换作曲家时这个比例会变，必须先摸源。
3. **并行子代理不稳定。** 一次派 4 个以上写手时，出现过半数在交付前被系统中断、空手而归。
   **每批 ≤2 个**，任务书里写明「拿不到谱例就写占位、立即交稿」。
4. **写手会写得很像、很空。** 这是本项目的核心风险，不是技术风险。派活时把「必须讲清的三到五个点」
   写成具体的音乐问题（「三种做法各自适合什么段落」），不要写成「讲清楚 XX 风格」。
5. **构建通过 ≠ 内容正确 ≠ 版权合规。** 前两者只能人看，第三者只能人判。

## 5. 交接验收

接手人应当在**半天内**独立完成下面五步。做不到，说明文档还不够，回来补：

1. 从 Mutopia 下载一个乐章 → 迁移到 2.26.0 → 编译 0 error。
2. 转成 english 音名 → 再编译 0 error。
3. 切出 8–16 小节，写成带围栏 `title`/`location`、`\tempo`、`% GM` 的代码块。
4. 挑一个选题写一篇 1500–3000 字的文章，**每个论断都能指到第 N 小节 + 音名**。
5. 在 `NOTICE.md` 登记来源与文章，跑通四步构建，提 PR。

## 6. 一句话

这个库的价值不在覆盖了多少作品，而在**一个正在写谱的人打开任意一篇，读完之后知道自己下一步该动哪个音**。

新加一个作曲家，标准不变：如果他读完你写的巴赫，还是不知道该动哪个音，那就是没写成。
