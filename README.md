# 音乐知识库

面向音乐创作 Agent 与人工协作者的作曲知识库。正文通过树状路径和关键词检索，
ABC/LilyPond 谱例会编译为可缩放乐谱、可播放 MP3 和可下载源码。

- 在线站点：<https://opencadenza.github.io/music-wiki/>
- 协作仓库：<https://github.com/OpenCadenza/music-wiki>
- 内容镜像：`viking://resources/music-wiki/`

## 协作方式

线上知识库以 `content/` 为维护对象，团队通过 fork 和 Pull Request 协作。

1. Fork `OpenCadenza/music-wiki`，在自己的仓库中建立分支。
2. 在分支中直接修改 `content/`，不要修改生成目录或构建产物。
3. 向 `OpenCadenza/music-wiki:main` 提交 Pull Request。
4. PR 会自动运行完整的构建检查，但不会部署到线上站点。
5. 维护者评审并合入 PR。
6. 合入 `main` 后，GitHub Actions 会自动重新构建并部署 GitHub Pages。

正常流程不需要手动触发 Actions。`workflow_dispatch` 仅用于维护者在服务异常或需要
重新发布时手动重跑。首次贡献者的工作流运行可能需要维护者批准；如果仓库为
`github-pages` 环境配置了审批规则，部署任务会等待指定维护者批准。

建议维护者在仓库设置中要求所有 `content/` 修改通过 Pull Request，并启用分支保护。

## 仓库结构

- `content/`：公开知识正文，通过 Pull Request 维护。
- `NOTICE.md`：谱例来源、版本与许可登记，不在知识正文内。
- `.vitepress/`：站点配置、主题和播放器组件。
- `.github/workflows/deploy.yml`：PR 检查与 `main` 自动部署。
- `public/`：站点公共静态资源；生成的 SVG、MIDI、MP3 和 manifest 不提交。

本地开发、工具链安装和单机发布步骤由项目内部文档维护，不属于公共协作说明。

## 内容组织规则

1. 每个公开目录使用 `index.md`，不使用 `README.md`。`index.md` 是该分支的实质导论：
   写这个作曲家、这个体裁在音乐上是什么，不写文件清单、检索方法、来源或证据边界。
2. 文章按选题组织，一篇回答一个创作问题。一个选题可以取多部作品的片段，同一部作品的
   不同片段也可以出现在多个选题里；不按"一部作品一篇"拆分。
3. 每个论断都要落到具体小节。谱例必须是真实作品，不接受原创教学模型、仿写或改写。
4. 谱例通常 8–20 小节，以能完整呈现一个乐思为准；只截论证需要的声部。
   统一使用 `\language "english"`，与站内其他谱例保持音名一致。
5. 同一段谱例只写一次，放在最详细讨论它的文章里；别处用链接引用。
6. 相对链接必须指向实际存在的文件。鼓励跨文章链接，但不要维护索引页、ID 表或别名表：
   检索由 OpenViking 与站点侧边栏承担。
7. 正文不写来源、版本、证据边界、免责声明、来源 ID 或检索词堆。这些记录在仓库根
   `NOTICE.md` 与项目内部构建文档中。
8. 生成的 SVG、MIDI、MP3、manifest、缓存和工具链文件不要提交。
9. 同一页面只允许一首谱例音频播放。开始播放或从头播放任意一首时，页面内其余播放器
   必须暂停。
10. PR 的自动检查会扫描当前全部谱例，谱例数量由内容动态决定。

## LilyPond 2.26.0 要求

每个 `lilypond` 或 `ly` 代码块必须且只能声明一次：

```lilypond
\version "2.26.0"
```

- 可执行语法必须与 2.26.0 一致；旧编码需要迁移时先运行 `convert-ly`、复核转换差异
  并重新编译，不能只修改版本字符串。
- 编译失败的谱例会阻止 PR 检查通过，也不会进入正式站点。

## 谱例要求

- 每个代码块必须自包含：不 `\include` 外部文件，`\score` 内完成全部排版。
- 统一写 `\language "english"`，音名用 `ef`、`bf`、`cs`，不要混入 `ees`、`bes`。
- 不需要在代码块前写元数据注释。谱例的稳定标识由文件路径与块序号自动生成。
- 作品、乐章、小节定位写在正文里，属于音乐信息，应当写清。
- 来源、版本与许可写进仓库根 `NOTICE.md`，不写进正文。

### 标题行（必填）

每个代码块**正上方一行**写加粗说明，作为这份乐谱的标题：

````markdown
**贝多芬 Op.2 No.1 第一乐章，mm.1–10**

```lilypond
\version "2.26.0"
\language "english"
...
```
````

格式固定为：`作曲家 作品号 乐章，mm.起始–结束`。构建脚本会把这一行同时用作
该谱例在播放器与索引里的标题；缺这一行视为不合规。同一篇里有多份谱例时，
每份各自一行，不编号。

### 速度标记（必填）

代码块里必须写出原谱的速度标记：

```lilypond
\tempo 4 = 190
```

不写的话 LilyPond 默认 60，播放会明显偏慢。速度值照抄来源乐章的 `\tempo`，
不要自己估一个"听起来差不多"的数字。

### 乐器与 GM 编号（必填）

每个 `\new Staff` 都要声明 MIDI 乐器，并在紧邻的一行写出 General MIDI 编号：

```lilypond
\new Staff = "up" {
  \set Staff.midiInstrument = "violin"
  % GM 41
  ...
}
```

`\set Staff.midiInstrument` 决定 LilyPond 的名字映射，`% GM <编号>` 是给构建脚本的
权威值：脚本按注释里的编号设置该声部的 MIDI 程序号。两者不一致时以编号为准。
**不写编号会退回钢琴音色**，非钢琴作品（弦乐四重奏、管弦乐、声乐）尤其要注意。

乐器名要写 LilyPond 认可的写法：钢琴是 `"acoustic grand"`（**不是** `"acoustic grand piano"`），
小提琴 `"violin"`，中提琴 `"viola"`，大提琴 `"cello"`。名字写错会有
`no such MIDI instrument` 警告，并静默退回钢琴。

### 不重复

同一段乐谱只出现一次，放在最详细讨论它的文章里。别处需要引用时，用链接指向
那份谱例所在的段落，不要复制代码块。构建校验会把重复的代码块判为错误。

### 找不到谱例时

不要因为拿不到乐谱就放弃选题。正文照常写，代码块位置用一行占位：

```markdown
**贝多芬 Op.106 第一乐章，mm.1–16**

> 谱例待补：Op.106 第一乐章 mm.1–16。
```

占位行同样保留作品、作品号、乐章与小节范围，方便后续补谱。文章里的分析与
论点不依赖谱例是否已经落地。

## 合并前检查

PR 会自动执行：

- 内容校验：每个目录有 `index.md`、无 `README.md`、无重复谱例、相对链接可达。
- 全部 LilyPond 与 ABC 谱例编译。
- SVG、MIDI、MP3 与 manifest 完整性检查。
- VitePress 构建和代表性页面冒烟测试。

任何步骤失败，PR 不应合入。合入 `main` 后会再次执行相同检查并部署站点。

## 许可

谱例来源与许可集中在仓库根 `NOTICE.md`，按文章分组记录作品、乐章、小节、取用渠道
与许可类型。站点页脚提供入口。`content/` 内不重复登记来源或许可。
