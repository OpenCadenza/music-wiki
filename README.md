# 音乐知识库

> **音乐学者子代理方案开发分支**：代码与研究文档由同一个仓库管理。
> 接手前请先阅读 [local/README.md](local/README.md)，从[Google Drive下载资料包](https://drive.google.com/file/d/18csDqCQFRM1LOUsRHQzZy98XmUS_deS2/view?usp=sharing)，校验并解压到仓库根目录后继续工作。
> 本分支不整体合并到main；正式发布另行选择审核通过的正文改动。当前仅完成交接准备，尚未启动正式写作。

> 当前处于资料预备与重建阶段。旧 content 已保存完整本地归档，正式轮首批就绪后替换；
> 旧稿不作为新文章知识来源。本轮不启动写作或发布。

面向音乐创作 Agent 与人工读者的音乐知识库。作者实际阅读教材、研究、作品与作曲家资料及原谱，
消化后写成理论、技法、风格、作品与背景文章；需要谱例时使用真实作品，
谱例在 CI 中编译为可缩放乐谱、可播放 MP3 和可下载源码。

- 在线站点：<https://opencadenza.github.io/music-wiki/>
- 协作仓库：<https://github.com/OpenCadenza/music-wiki>
- 内容镜像：`viking://resources/music-wiki/`

## 写一篇文章要满足什么

先看这张表。工程项由 `pnpm validate` 与 CI 检查，阅读、理解与论证由作者和编辑复读判断。

| 项 | 要求 |
| --- | --- |
| 目录 | 每个公开目录有 `index.md`，且写实质导论 |
| 选题 | 从阅读中自主发现有价值的问题，不限作曲家或主题，可以取多部作品的片段 |
| 论断 | 主要观点有真实阅读和推理支撑；具体技法分析说明相关音乐对象与机制 |
| 谱例 | 真实作品，长度服从解释需要；不接受原创教学模型或仿写充作原作 |
| 编码 | `\version "2.26.0"` 恰好一次，`\language "english"`，代码块自包含 |
| 标题 | 代码围栏属性 `title="作曲家 作品名称 作品号 乐章"` + `location="mm.起–止"` |
| 速度 | 写 `\tempo`；保留来源标记，额外试听数值在生产记录中说明 |
| 乐器 | 每个 `\new Staff` 写 `midiInstrument` + `% GM <编号>` |
| 复用 | 同一段谱例全库只出现一次，别处用链接 |
| 来源 | 来源与许可登记在根 `NOTICE.md`，详细阅读与生产记录在正文之外 |

## 协作方式

本开发分支的研究协作和提交采用[单仓库接手说明](local/docs/交接/README.md)。下述fork／PR规则描述面向main的公开内容发布流程，不表示本研究分支可以整体合入main。

正式知识正文维护在 `content/`，团队通过 fork 和 Pull Request 协作。来源信息随文章交付，
由维护者统一写入 `NOTICE.md`；不要修改生成目录或构建产物。

1. Fork `OpenCadenza/music-wiki`，在自己的仓库中建立分支。
2. 在分支中编辑 `content/`，并提交对应来源登记信息；`NOTICE.md` 由维护者协调更新。
3. 向 `OpenCadenza/music-wiki:main` 提交 Pull Request。
4. PR 会运行完整构建检查，但不会部署。
5. 维护者评审并合入。
6. 合入 `main` 后自动重新构建并部署 GitHub Pages。

正常流程不需要手动触发 Actions，`workflow_dispatch` 只用于服务异常时重跑。首次贡献者的
工作流可能需要维护者批准；若 `github-pages` 环境配置了审批规则，部署会停在等待审批。
建议维护者要求所有 `content/` 修改通过 PR，并启用分支保护。

## 目录与选题

**目录页写内容，不写清单。** `index.md` 是该分支的实质导论：讲这个作曲家、这个体裁在音乐上
是什么、有哪些值得追的问题。不写文件列表、检索方法、来源或证据边界——检索由 OpenViking
与站点侧边栏承担。

**从阅读形成选题。** 作者自主选择有价值的理论、技法、风格、作品或背景问题，不按作品清单机械填篇。
一个选题可以取多部作品的片段，同一作品的不同片段也可进入不同选题。文章不设固定字数、作品数或章节模板。

**解释要有根据。** 实际读过的资料和音乐现象支撑主要论点。具体技法分析要说明哪个对象怎样起作用，
但概念、背景与风格阐释不要求每句话都有小节、音名和拍位。允许作者有根据的独立分析，不逐句寻找文献原话。

**正文写音乐。** 来源清单、许可、下载与阅读记录、证据登记、免责声明、来源 ID 和检索词堆
放在 `NOTICE.md` 或本地生产记录中。正文不做形式化来源清单，也不为检索堆结构化字段。

**链接可以多，索引不要建。** 相对链接必须指向实际存在的文件；讨论 Op.106 的赋格时可以直接
链到讲赋格的那篇。但不要维护索引页、ID 表或别名表——那是检索层的事。


### 目录结构

```text
content/
├── index.md                      # 定位与材料／结构／音响三个尺度
├── techniques/                   # 问题轴：可跨语境推广
│   ├── index.md
│   ├── material/                 # 动机、乐句、主题、细胞
│   ├── structure/                # 曲式、段落、调性布局、终止、比例
│   ├── harmony/                  # 调性关系、和声语汇、半音体系
│   ├── counterpoint/             # 模仿、卡农、赋格、声部进行
│   ├── rhythm/                   # 节拍、速度、节奏型、弹性速度
│   └── sound/                    # 音区、织体、厚度、力度、配器
├── composers/                    # 语境轴：某人某体裁的具体做法
│   ├── index.md
│   └── <作曲家>/
│       ├── index.md              # 总体特点，写音乐实质
│       └── <体裁>/
│           ├── index.md          # 体裁的问题地图
│           └── <选题>.md
├── ensembles/                    # 语境轴：编制的惯例与限制
│   └── <编制>/
├── styles/                       # 语境轴：非作曲家体系的风格
│   └── <风格>/
└── notation/                     # 工具轴：记谱与实现
    └── <主题>.md
```

作者按选题自主决定文章位置，可以新建子目录。技法六维保留；没有内容的目录不预建空页。

## 谱例要求

### 版本与语言

每个 `lilypond` 或 `ly` 代码块必须且只能声明一次：

```lilypond
\version "2.26.0"
```

- 代码块必须自包含：不 `\include` 外部文件，`\score` 内完成全部排版。
- 统一写 `\language "english"`，音名用 `ef`、`bf`、`cs`，不要混入 `ees`、`bes`。
- 旧编码迁移先运行 `convert-ly`、复核差异再重新编译，不能只改版本字符串。
- 编译失败的谱例会阻止 PR 检查，也不会进入正式站点。

### 标题与定位（必填）

标题和位置写在代码围栏的第一行：

````markdown
```lilypond title="贝多芬 第1钢琴奏鸣曲 Op.2 No.1 第一乐章" location="mm.1–10"
\version "2.26.0"
\language "english"
...
```
````

字段约定：

- `title`：作曲家、作品名称、作品号和乐章，例如 `贝多芬 第1钢琴奏鸣曲 Op.2 No.1 第一乐章`。
- `location`：速度标记、排练号或小节范围，例如 `Grave，mm.1–10`。
- `id`：可选稳定标识。需要外部链接或跨文章引用时使用：

````markdown
```lilypond title="贝多芬 第1钢琴奏鸣曲 Op.2 No.1 第一乐章" location="mm.1–10" id="beethoven-op2no1-i-mm1-10"
...
```
````

属性值使用双引号，不支持未转义的双引号、未知字段或重复字段。`id` 只允许小写字母、
数字、点、下划线和连字符，并以字母或数字开头。未写 `id` 时继续按文件路径和块序号
生成默认 ID。

构建器直接读取围栏属性，不再依赖标题行与代码块之间的空行或 Markdown 段落。VitePress
把 `title` 和 `location` 作为乐谱卡片的两级标题渲染，`title` 使用正常字重强调，
`location` 使用次级文字样式；标题在页面中只显示一次。

构建器仍兼容旧的加粗标题行写法，但
`pnpm validate` 会对这类代码块输出迁移提示；新建或修改谱例时一律使用围栏属性，
不要新增加粗标题行。两种写法同时存在会直接报错。

### 速度标记（必填）

代码块保留原谱的速度标记，并提供合适的播放速度；数值仅作格式示例：

```lilypond
\tempo 4 = 190
```

避免缺省播放速度造成明显失真。有明确来源数值时按来源保留；为试听另选的数值要在生产记录中说明，
不能冒称作曲家的原始标记。

### 乐器与 GM 编号（必填）

每个 `\new Staff` 都要声明 MIDI 乐器，并在紧邻的一行写出 General MIDI 编号：

```lilypond
\new Staff = "up" {
  \set Staff.midiInstrument = "violin"
  % GM 40
  ...
}
```

`midiInstrument` 决定 LilyPond 的名字映射，`% GM <编号>` 是给构建脚本的权威值：脚本按注释
里的 0–127 程序号设置该声部，两者不一致时以编号为准。不要混用 1–128 的编号表。
乐器名称无效时可能回落到钢琴，非钢琴作品尤其要明确 GM 编号。

移调乐器的 `\transposition` 也按 `\language "english"` 的音名写：B♭ 调写 `\transposition bf`、
E♭ 调写 `ef`、D 调写 `d`。写成 `bes` 会在 english 下报 `Expecting pitch, found bes`。
乐器名要写 LilyPond 认可的写法：钢琴 `"acoustic grand"`（**不是** `"acoustic grand piano"`），
小提琴 `"violin"`，中提琴 `"viola"`，大提琴 `"cello"`。名字写错会有 `no such MIDI instrument`
警告，并静默退回钢琴。

### 长度与截取

长度以能完整呈现相关乐思及上下文为准，可以超过一个乐句；只截论证需要的声部，不整乐章搬运。
作品、乐章、小节定位写在正文里，属于音乐信息，应当写清。

### 不重复

同一段乐谱只出现一次，放在最详细讨论它的文章里。别处引用时用链接指向那份谱例所在的段落，
不要复制代码块。构建校验会把完全重复的代码块判为错误——这既是规矩也是技术约束：
谱例按代码哈希查 manifest，重复会串号。

### 找不到谱例时

不要因为拿不到乐谱就放弃选题。正文照常写，代码块位置用一行占位：

```markdown
**贝多芬 Op.106 第一乐章，mm.1–16**

> 谱例待补：Op.106 第一乐章 mm.1–16。
```

没有代码块时仍可用一行加粗文字和引用块表示待补；这不属于谱例元数据。占位保留作品号、
乐章与真实小节范围，方便后续补谱；位置不明则注明待定位。
占位只解决代码暂缺，中心解释仍须来自已实际阅读的资料，不能用模型记忆填补未做的研究。

### 播放行为

同一页面只允许一首谱例音频播放：开始或重播任意一首时，页面内其余播放器会暂停。

## 提交纪律

生成的 SVG、MIDI、MP3、manifest、缓存和工具链文件一律不提交。`.tools/` 与
`public/notation/` 由构建生成，丢失后可重建；GitHub 也会拒绝大于 100 MiB 的普通文件。
不要手工修改 `.publication.json`。

## 合并前检查

PR 自动执行，任一失败都不应合入：

- 内容校验：每个目录有 `index.md`、内容目录无 `README.md`、`index.md` 有一级标题、
  无重复谱例、相对链接可达、`NOTICE.md` 存在。
- 全部 LilyPond 与 ABC 谱例编译，谱例数量由内容动态决定。
- SVG、MIDI、MP3 与 manifest 完整性检查。
- VitePress 构建与代表性页面冒烟测试。

合入 `main` 后会再次执行相同检查并部署站点。

## 许可

文章资料及谱例来源与许可集中在仓库根 `NOTICE.md`，按文章记录实际采用资料、作品、乐章、小节、取用渠道与许可
类型，站点页脚提供入口。`content/` 内不重复登记来源或许可。构建通过只证明代码可编译，
不证明音乐学内容或版权判断正确——谱例的截取范围与许可需要人工复核。
