# 音乐知识库：读谱、理解，然后写出来

这是一个关于音乐理论、作曲技法、作曲家风格与作品细节的知识库。它的目标不是堆术语，而是让读者（人，或将要使用 OpenViking 检索的创作 Agent）读完一篇之后，能真正理解一段音乐**为什么这样写**——作曲家做了一个决定，这个决定解决了什么问题，代价是什么。

## 这个分支的特点

本分支是**知识生产的开发分支**，与发布站点的内容在同一仓库中迭代：

- **正文在 `content/`，研究过程在 `local/`。** 每篇文章都有对应的研究归档——作者实际读了哪些资料、用了哪些谱源、还有哪些缺口。正文只写音乐，生产细节留在 `local/`。
- **逐篇归档、逐篇提交。** 每篇文章成稿后都有自己的版本快照，修改与修订都在 Git 历史里可追溯；研究进行中不发布，发布另行从审核后的正文选取。
- **谱例经过独立核验才进正文。** 谱例代码必须能编译，音高必须与可靠谱源逐音一致；交付者不核验自己的作品，核验者不生产。找不到可靠谱源的片段，正文保留真实定位的占位，不编造。
- **资料库与代码分离。** 原始资料、可读副本与大型谱源保存在本地研究区（`local/` 的忽略目录与独立资料包），Git 中只保留轻量的入口、来源卡与交付登记。

## 知识库是怎么构建的：一套学者 Agent 工作流

这个知识库由一组扮演不同角色的 Agent 协作产出，流程本身也是这个分支想科普的内容之一。

**角色分工**

| 角色 | 做什么 |
| --- | --- |
| 音乐学者（若干） | 从阅读库实际阅读文献与谱面，**自由选择选题**，形成自己的理解并写作 |
| 资料收集助手 | 查重、寻找并保存新资料，负责新资料的初步整理与登记 |
| 谱例编码助手 | 把学者指定的真实片段做成可编译的 LilyPond 代码，交付前核对谱源 |
| 谱例核验员 | 独立逐音核对交付的谱例，判「一致／有差异／无法核验」 |
| 编辑复读 | 每批文章结束后集中复读整批：理解是否成立、论证是否连续、跨篇是否有重复或矛盾 |

**流程要点**

1. **先有资料，后有题目。** 学者先读文献（教材、论文、版本导言、乐器资料、原生乐谱编码），从阅读中发现问题，而不是先定题目再找证据。题目前不设列表，不预设结论。
2. **自由选题，共享资料。** 选题不限作曲家与体裁；学者之间通过任务板互相可见，相近题目先沟通；新取得的资料对所有学者开放。
3. **从阅读到论述有边界。** 文章分得清三件事：资料作者说了什么、谱面显示了什么、作者自己推导了什么。自己的归纳必须标注为推导，不能包装成已有理论。
4. **谱例只认真实来源。** 一段谱例要么来自核对过的机器可读谱源（Kern、DCML、MusicXML），要么来自可靠的排版工程；人工转写的旧谱需经核验才能使用。找不到就如实占位。
5. **成稿后复读。** 编辑复读只检查主要理解、论证连续性与跨篇关系，不逐句挑刺；复读意见分给作者修订，修订再提交。

这样产出的一篇文章，背后有一条可追溯的链：**读了什么 → 发现什么问题 → 用什么谱面/文献证据 → 得出什么结论 → 有哪些未解决的缺口**。读者顺着这条链，既可以学到结论，也可以学到"音乐分析是怎么做出来的"。

## 从哪读起

- [技法（techniques/）](techniques/)：按"要解决的问题"组织的知识——材料、结构、和声、音响、对位、节奏六个方向。
- [编制（ensembles/）](ensembles/)：从乐器物理与声学条件理解重奏编制——管乐五重奏、钢琴三重奏、弦乐四重奏等。
- [作曲家（composers/）](composers/)：具体作曲家在自己熟悉的体裁里怎么解决问题——巴赫、贝多芬。
- [风格（styles/）](styles/)：非个人体系的审美与惯例如何演变。
- [记谱（notation/）](notation/)：符号、编码与声音之间的转译——八度怎么丢、演奏法怎么丢、证据怎么采信。

每个目录的 `index.md` 介绍这一层关心的音乐问题；正文之间的链接表示问题之间的关联。谱例仍在持续补全中：一部分文章已嵌入核验过的真实乐谱，其余以真实定位占位并逐一补齐。
